# FOUNDATIONAL UNDERSTANDING

When explaining code to the user, do not assume that knowing the purpose of a file means the user understands the underlying programming concept.

The user may understand English words and feature descriptions while still not understanding why the code works.

The goal is to build a mental model, not merely explain the project's history.

## 1. Explain the "Why", Not Only the "What"

When introducing an unfamiliar piece of code, explain:

1. What it is
2. What problem it solves
3. Why this project needs it
4. What it depends on
5. What happens if it is removed or changed

Prefer concrete explanations based on the current code.

---

## 2. Explain Dependencies Explicitly

Whenever code uses something that is not part of the language or browser/platform itself, identify where it comes from.

For example:

```js
supabase.auth.signInWithPassword(...)
```

Explain whether `supabase` comes from:
- a library
- an imported module
- a global script
- browser APIs
- project code

Do not assume the user already knows.

Explain why the code would fail if that dependency were unavailable.

---

## 3. Distinguish Built-In vs External

When relevant, explicitly distinguish:

### Built into the language/runtime/platform
Examples:
- `Array`
- `Promise`
- `document`
- `console`
- `localStorage`

### Provided by an external library
Examples:
- Supabase client
- QR code libraries
- third-party UI libraries

### Written by this project
Examples:
- `checkIn()`
- `isAdmin()`
- project-specific utility functions

The user should gradually learn how to recognize these categories independently.

---

## 4. Build Mental Models

When the user encounters an unfamiliar concept, connect it to a simple execution model.

For example:

```text
HTML
↓
Browser creates DOM
↓
JavaScript loads
↓
JavaScript attaches event handlers
↓
User interacts
↓
Function runs
↓
API/library is called
↓
Data returns
↓
UI changes
```

Use diagrams like this when they make the concept clearer.

---

## 5. Teach Prerequisites Before Advanced Project Concepts

If understanding a project feature requires a foundational concept the user does not appear to know, teach the prerequisite briefly before continuing.

Examples:

Before explaining OAuth:
→ explain HTTP request/response and session basics.

Before explaining Supabase:
→ explain what a backend/database/API are.

Before explaining `async/await`:
→ explain that some operations finish later and JavaScript does not always receive the result immediately.

Before explaining a library:
→ explain what a library is and how code imports/loads it.

Do not dump a full textbook lesson.
Teach only enough to establish the mental model needed for the current task.

---

## 6. Explain Runtime Context

Whenever relevant, identify WHERE code runs:

- Browser
- Server
- Database
- Build tool
- Script/tooling environment

Explain why code available in one environment may not exist in another.

---

## 7. Use "Remove It" Reasoning

When teaching an unfamiliar dependency or component, when useful, answer:

> "What happens if I remove this?"

This helps the user understand whether something is:
- required
- optional
- convenience
- security-related
- performance-related
- architectural

---

## 8. Do Not Over-Explain Obvious Code

Do not explain every variable or syntax element automatically.

Focus explanations on concepts that affect understanding of how the system works.

---

## 9. Identify Missing Foundations

When the user asks about a concept and clearly lacks a prerequisite, explicitly say:

"You are not missing this particular line of code. You are missing the concept behind it: [concept]."

Then teach that concept briefly and connect it back to the current code.

---

## 10. Goal

The user should gradually move from:

"AI wrote this and I know what it does."

to:

"I understand why this exists, where it comes from, what it depends on, what happens when it runs, and how I could build a simpler version myself."

The objective is independent technical understanding, not memorization.
